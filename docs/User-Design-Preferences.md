# 菜猪猪：用户设计偏好与协作记忆

> 最后整理：2026-09-18
>
> 用途：后续功能设计、界面调整与技术决策时的可复用上下文。除非用户明确更新，本文件中的“已确认”项应视为默认约束；“暂定推断”必须在影响范围较大时重新确认。

## 1. 产品定位（已确认）

- 产品名：**菜猪猪——家庭厨房管理软件**。
- 核心价值：菜谱、今日菜单、采购和库存管理；用户数据可靠性比花哨功能更重要。
- 目标使用方式：手机上的可安装 Web App / PWA，优先覆盖 iPhone 与 Android；当前不依赖 Mac、Xcode 或应用商店。
- 常用用户：两人，但当前先采用**一个共享账号**，两台设备登录同一邮箱与密码，共享所有数据。
- 使用场景是家庭而非企业仓储：不做复杂仓储、批次财务、账号社交、推荐流或视频识别。

## 2. 信息架构与功能优先级（已确认）

1. 菜谱与今日菜单是两个独立的主要区块；**今日菜单应显示在我的菜谱之前**。
2. 用户从菜谱加入今日菜单时，菜谱食材自动进入采购清单；移出今日菜单时，相关自动采购项自动移除。
3. 菜谱多时，首页只显示有限预览，提供“展开/查看全部”弹窗，避免首屏拥挤。
4. 内容导入功能目前暂时移除，后续再完善；不要主动重新加入入口。
5. 采购、库存的联动是高优先级：采购完成后进入库存，而不是让用户重复录入食材信息。

## 3. 菜谱交互偏好（已确认）

- 新建菜谱保持精简：不显示份量、耗时、来源字段；默认按单人份处理。
- 食材通过“＋ 添加食材”逐条添加，每条分别填写名称、数量、单位；不要求用户输入特定文本格式。
- 步骤支持从连续文字中进行简单的编号/标点拆分，减少手动换行。
- 默认标签为：`素菜`、`荤菜`、`汤类`。
- 标签使用下拉/多选，而非手动自由输入；允许用户通过“添加自定义标签”创建，并在下次复用。
- 加入今日菜单时，用户填写可为小数的份量；所需食材按菜谱基准份量换算，采购数量向上取整。
- 烹饪模式：逐步显示、有前后切换；食材区标题使用**“所需食材”**，不用“本步食材”。

## 4. 采购与库存规则（已确认）

### 单位与食材

- 同一食材应统一单位，避免“颗/个”等等价单位形成多条记录。
- 已支持的等价单位范例：`颗、枚、只、粒 → 个`；`g → 克`；`kg → 千克`；`ml → 毫升`；`l → 升`。
- 不能可靠换算的包装单位（袋、盒等）不能擅自合并；未来需要用户定义换算关系。
- 采购页按“规范化食材名 + 规范化单位”合并；库存页按食材汇总，但库存事件保留独立记录。

### 批次、日期与寿命

- 同一种食材可能在不同日期采购，必须形成独立入库批次，保质期分别计算。
- 入库批次需保存：食材、数量、单位、采购日期、入库日期/创建时间、保质期天数、到期时间、来源采购项。
- 到期时间以 `采购日期 + 保质期天数` 计算，而不是以点击入库时间计算。
- 库存中展示到期倒计时。

### 事件与余额

- 库存余额由入库、消耗、调整事件汇总得到；库存不可为负数。
- 删除库存事件采用**直接删除**，但若删除会造成余额负数则拒绝删除。
- 事件流水支持归档；归档后默认折叠，当前流水限制展示最近 5 条。
- **调整不是增减数量**：用户输入盘点后的目标库存，系统自动记录目标值与差额；流水显示“调整至 X 单位”。
- 消耗采用批量模式：弹窗列出所有现有库存；每项默认消耗全部，可用数字框修改；一次确认生成多条消耗事件，任何超量都不能部分提交。

### 采购入库

- 单项采购勾选仍可入库，适用于只买到部分食材。
- 采购页另有“批量入库”：列出全部未完成采购项，食材、数量、单位自动带入；用户逐项只填写保质期，采购日期默认当天；确认后批量创建入库事件并批量勾选采购项。

## 5. 视觉与文案偏好（已确认）

- 整体气质：温暖、轻量、家庭厨房感，避免企业后台或复杂表格风格。
- Logo / 品牌形象：使用“菜猪”而非单纯文字或抽象图标；底部导航和品牌页应更精致、易辨识。
- 页面首屏不应塞满长列表；优先卡片、摘要、折叠和“查看全部”。
- 表单应最小化用户输入：能自动带入的食材、数量、单位、采购日期不要重复要求填写。
- 对可能造成数据损失的操作避免提供醒目的快捷入口；已移除“重置演示数据”。
- 文案直接、清楚、动作导向；例如“批量入库”“调整后库存”“所需食材”。
- 强调状态和主要操作使用与“入库”一致的高亮主色；临期提醒等状态模块采用圆角矩形容器，内部条目也保持同一圆角体系，避免突然变为纯文本列表。

## 6. 数据与云端偏好（已确认）

- 数据可靠性是核心要求，不能把浏览器本地存储当成唯一备份。
- 当前实现：浏览器本地优先；共享账号登录后同步结构化业务数据到 Supabase。
- 云端当前同步：菜谱文字/食材/步骤、今日菜单、采购清单、库存事件、标签等状态。
- 云端当前未完成：菜谱图片仍在设备 IndexedDB，不可宣称已完成完整图片云备份；需要后续接入 Supabase Storage 私有桶。
- 保留 JSON 导入/导出作为额外恢复手段；导入会替换当前本地状态，需清晰提示。
- 前端只可使用 Supabase Project URL 与 publishable/anon key；绝不把 `service_role` 管理员密钥放入代码、GitHub 或聊天。
- 数据库必须启用 Row Level Security；共享账号模式意味着两人拥有相同权限、没有个人操作审计。

## 7. 技术与交付习惯（已确认）

- 当前环境为 Windows：可完成 PWA、纯 Swift 模块、API、静态检查和测试；不可声称已在 Xcode、iOS Simulator、Share Extension 或 App Intent 中构建验证。
- PWA 正式地址：<https://hingo1330.github.io/caizhuzhu/>。
- GitHub 仓库：<https://github.com/HINGO1330/caizhuzhu>。
- 使用 Git 功能分支开发，避免直接在 `main` 做日常改动；完成测试后再合并发布。
- 不执行破坏性 Git 操作（如 `reset --hard`、丢弃用户改动）。
- 实现遵循 TDD：先写失败测试、确认失败原因、最小实现、运行完整测试。
- 用小批次改动持续验证；完成时报告真实测试、静态检查、Git 状态和发布状态。
- 修改发布后应附上正式链接或明确说明 GitHub Pages 仍在更新。

## 7.1 AI 步骤整理偏好（已确认）

- AI 的第一阶段仅用于“菜谱制作步骤整理”，不自动解析视频或图片。
- 流程为：粘贴原文 → 本地规则预览 → 用户不满意时主动点击智能整理 → 预览 AI 结果 → 用户采用并保存。
- AI 不能直接覆盖原文或自动保存菜谱；用户始终保留修改与拒绝结果的权利。
- 采用低成本安全中转：Cloudflare Worker 保存 API Secret，GitHub Pages 前端不保存任何 AI 密钥。

## 8. 协作与沟通偏好（已确认）

- 用户通常希望直接推进，不需要反复讨论已经确认的产品范围。
- 只有会实质改变产品范围、数据模型或外部权限的选择才需要先询问。
- 回答必须基于事实：区分已验证事实、合理推断和暂未验证的事项；不要为了迎合而默认同意错误前提。
- 对数据丢失、同步冲突、安全、平台限制等风险，应主动且明确说明。
- 提供修改结果时，优先说清用户能感受到的变化，再给测试与链接。

## 9. 暂定推断（需在重大改动前复核）

- 用户偏好先做低成本、可自行维护的方案，再根据真实使用量升级为付费或更复杂的架构。
- 用户更重视“少输入、自动联动”的体验，而不是为每个边界情况增加大量配置页面。
- 未来若从共享账号改为两人独立账号，应建立“家庭空间 + 成员关系”，而不是继续共享密码。
- 未来单位换算应以“食材主档 + 单位换算规则”演进，而不是只扩大字符串替换表。
